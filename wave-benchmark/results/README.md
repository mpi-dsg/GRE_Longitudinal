# Results

Every CSV behind the paper. All measured on identical dual-socket Xeon Gold 6134M servers
(16 physical cores, 755 GB, oneTBB), each otherwise idle while measuring, and every comparison
uses runs from one server. The early directories (`scale400_*` through `lockstats`) come from
one server; `r6`, `r7`, `r12`, and `final_cmp` from a second; `r9`, `r10`, and `r11` from a
third; `r8` from a fourth, which also reruns the baseline and the design so the ablation is
compared on one machine; all of `r13` from one server. Where a table combines servers, the baseline measured on each agrees
within 2%.

Generated by `../bench.cpp`. The final run sets (`r6` to `r13`) were produced by
`../runs/mq6.sh` to `mq13b.sh` on the final binary, which includes the ALEX-OL fixes
in `alexol-sidebuf.patch`; each script's `*_verify.log` in the directory holds the recall and
exhaustive checks.

The `ns400`, `seeds400`, `mix400` and `thr` directories were measured on the second server;
`q14_verify.log` holds their recall checks. Earlier design runs (`mech_*`) predate the ALEX-OL
fixes and are replaced by `r6`.
Current-driver CSVs have 23 fields per `x` row (the 17 below plus `r_*` read columns and
`batch_ns`, `mem`), and `LOCK2` rows carry: retry, retry_smo, retry_ins, parentspin, fg_smo,
bg_smo, bg_skip, smo_ns, smo_max_ns, side_ins, side_read, side_full, smo_split, retry_noside,
split_ns. `analysis/mk_mech.py` and `analysis/mk_panel.py` parse them. `CPU` rows carry tag, seed, threads, batch and CPU nanoseconds over the timed interval.

## Column layout

Most files have 17 columns:

```
tag,index,seed,threads,batch,keys,p50_ns,p99_ns,p999_ns,p9999_ns,max_ns,
n_gt10us,n_gt100us,n_gt1ms,n_ops,batch_ns,mem_bytes
```

`lookup_cost` has 23, inserting six read-path columns before `batch_ns`:

```
r_p50_ns,r_p99_ns,r_p999_ns,r_max_ns,r_gt100us,r_ops
```

`lockstats` files additionally carry `LOCK,` lines:

```
LOCK,tag,seed,threads,batch,keys,retry,parentspin,calls,lock_busy,validate_fail,read_denied
```

Headers are stripped from most files because the runner filters with `grep -E "^x,"`. The
column names above are authoritative.

## Read the counts, not the percentiles

`n_gt10us`, `n_gt100us` and `n_gt1ms` are the primary tail metric. A wave produces roughly one
slow insert per expanding node, and whether a percentile sees them depends on how that count
compares with its rank cutoff, which depends on batch size. On 400M runs (medians over three seeds), p99.9 over
12.5M-operation batches reports a wave-to-quiet concentration of 1.8x where counting inserts
over 100us reports 828x. Percentiles also flatter any change that merely spreads the same slow
operations more thinly, which produced a result we withdrew. Section 4 of the paper ("Why Percentiles Miss the Bursts") has the
full argument.

`mem_bytes` is a free diagnostic on its own: a synchronized cohort expanding together makes a
staircase, an unsynchronized one makes a ramp.

## Superseded, deliberately not kept

Two bodies of runs were discarded rather than stored, because keeping wrong numbers next to
right ones invites mistakes:

- A full sweep using `std::thread` instead of OpenMP. LIPP-OL and SALI index per-thread node
  pools by `omp_get_thread_num()`, which returns 0 for every raw thread, so they shared one
  unsynchronized pool. LIPP-OL crashed; SALI raced silently and returned plausible flat numbers.
- A 400M run measured only with percentiles, before the slow-operation counts existed.

Both are described in `../implementation-notes.md`.
